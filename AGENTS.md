# Правила для агента (AGENTS.md)

Этот файл обязателен к прочтению перед началом любой работы в репозитории. Его читает любой агент (Claude Code, Copilot, Codex и т.д.). `CLAUDE.md` ссылается сюда.

## 0. Что это за проект

Веб-система учёта мероприятий по уходу за зелёными насаждениями вместо базы MS Access. Полное описание: [`docs/TZ.md`](docs/TZ.md). Разбор старой системы: [`docs/ANALYSIS.md`](docs/ANALYSIS.md). Журнал работ: [`workbook.md`](workbook.md).

## 1. Порядок работы при старте сессии

1. Прочитать `AGENTS.md`, `docs/TZ.md`, затем `workbook.md` целиком, особенно последние записи и раздел «Текущее состояние / Следующие шаги».
2. Выполнить `git pull`, `git status`, `git log --oneline -10`. Сверить реальное состояние репозитория с `workbook.md`. Если они расходятся, верить репозиторию и записать расхождение в `workbook.md`.
3. Только после этого начинать работу.

## 2. Журнал `workbook.md` (обязательно)

Назначение: восстановить контекст, если работу продолжит другой агент или среда сбойнёт.

- Запись делается после каждого значимого шага: выполненные действия, принятые решения (с причиной), изменения в файлах, найденные проблемы, неудачные попытки.
- Формат записи: `## YYYY-MM-DD HH:MM — краткий заголовок`, затем списки «Сделано», «Решения», «Изменённые файлы», «Проблемы / не проверено».
- Записи только добавляются в конец раздела «Хронология». Старые записи не переписываются; ошибку исправляют новой записью.
- В конце файла поддерживается блок «Текущее состояние / Следующие шаги». Его перезаписывают при каждом обновлении.
- Писать только то, что реально произошло и проверено. Если что-то не запускалось или не проверялось, так и указать. Нельзя записывать «работает» по предположению.
- Коммит с изменением кода и запись в `workbook.md` делаются вместе, в одном коммите или в соседних.

## 3. Промежуточные push (обязательно)

Цель: не потерять прогресс при сбое рабочей среды агента.

- Делать `git commit` и `git push origin main` после каждого завершённого логического шага, а не только в конце. Ориентир: не реже чем раз в 20–30 минут активной работы или после любого результата, который жалко потерять.
- Перед длительной или рискованной операцией (массовое изменение, миграция, импорт) сначала закоммитить и запушить текущее состояние.
- Сообщения коммитов на русском или английском, в повелительном наклонении, по смыслу: `Добавить модель Norm и миграции`.
- Перед `git add` просмотреть `git status`. Не добавлять секреты, `.env`, файлы БД, `.venv`, резервные копии.
- Если push не прошёл, сообщить об этом в первой фразе отчёта и записать в `workbook.md`. Нельзя молча продолжать.
- Не делать force-push, `git reset --hard`, не удалять ветки и не переписывать историю без явного разрешения владельца.

## 4. Секреты и безопасность

- Токены доступа (GitHub PAT и любые другие) нельзя записывать в файлы репозитория, в `workbook.md`, в сообщения коммитов и в логи. Токен используется только как переменная окружения или через менеджер учётных данных git, не сохраняется в `.git/config` (удалённый URL без токена).
- Репозиторий может быть публичным. Реальные рабочие данные (ФИО, акты, БД) не коммитить в новые файлы без согласия владельца. Исходные `.accdb` уже лежат в репозитории (см. `workbook.md` про это замечание).
- Секреты приложения (SECRET_KEY, пароли БД) хранятся в `.env`, который указан в `.gitignore`. В репозитории только `.env.example`.
- Писать безопасный код: параметризованные запросы, экранирование вывода, защита от CSRF, проверка прав. Не вставлять пользовательский ввод в SQL строкой.

## 5. Правила разработки

- Среда владельца: Windows + Python 3.12 + VS Code + GitHub. Код и скрипты должны работать на Windows без правки вручную. Не использовать bash-специфику, пути писать через `pathlib`.
- Всё запускается одной командой `python run.py` (см. ТЗ, раздел 9). Любое новое действие, которое требует ручных шагов, надо встроить в `run.py` или описать причину, почему это невозможно.
- Зависимости только в `requirements.txt` с зафиксированными версиями. Новые зависимости добавлять осознанно и записывать причину в `workbook.md`.
- Минимум лишнего: не добавлять функции и абстракции сверх ТЗ. Комментарии только там, где неочевидно ПОЧЕМУ.
- Данные пользователя неприкосновенны. Любой скрипт, который меняет или удаляет данные, должен сначала делать резервную копию БД и поддерживать режим `--dry-run`.
- Импорт из Access идемпотентный: повторный запуск не создаёт дублей (ключ `legacy_id`).
- Менять структуру БД только через миграции Django, не вручную.
- Для каждой бизнес-формулы (расход, норма, ДВ, бензин) есть юнит-тест с числами, сверенными со старой системой.
- Интерфейс и все пользовательские тексты на русском языке. Код, имена полей и коммиты можно на английском.
- Изменения UI проверять в браузере. Если проверить нельзя, прямо написать в отчёте, что UI не проверялся.

## 6. Отчёт о результатах

- Сообщать то, что реально произошло. Если что-то не запускалось, не проходило или дало другой результат, это сказать в первой фразе.
- Если работа остановлена до завершения, первая строка говорит об этом и называет, что осталось.
- Итог одним-двумя предложениями: что изменено и что дальше.
