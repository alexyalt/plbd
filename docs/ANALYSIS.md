## 2. Предметная область

Организация ухаживает за зелёными насаждениями на нескольких объектах.

- **Объект** (`location`): площадка, например `КП-3`, `СК-8`, `ОТ-Масандра`, `Киммерийский сад`. Всего 35. У объекта есть `loc_code`, он нужен в отчёте о списании (номер договора/отгрузки для бухгалтерии).
- **Куртина** (`place`): участок внутри объекта (например «Нижняя полка», «Кипарисовая аллея»). Всего 312, поле `parent` хранит название объекта текстом. В поле `content` текстом через `;` записан состав растений куртины (заполнено у 247).
- **Растение** (`flora`): справочник из 348 названий и латинских названий.
- **Агроном** осматривает объект и вносит **акт осмотра / проблему** (`inspection`): где, какое растение, сколько, что случилось, причина, какие меры назначены.
- **Причина** выбирается из четырёх справочников: вредители (`pest`, 91), болезни (`sickness`, 78), физиология (`physiology`, 26), другое (`other`, 21).
- **Препарат** (`farma`, 191 запись): норма, единица, класс, способ применения и складские реквизиты.
- **Садовник** (`person`, 28) выполняет задание и сообщает, сколько литров рабочего раствора израсходовано. По этому факту записывается **обработка** (`treat`).
- Раз в период готовится **отчёт о расходовании ТМЦ** со списанием препаратов (флаг `write-down`).

## 3. Сквозные сценарии (как система работает на деле)

```
Агроном: форма «Inspection ADD»          Агроном/бригадир: печать
  └─ создаёт акт осмотра (inspection)      ├─ акт обследования (insp_report.xltx)
       done=0, inWork=0                    └─ задание садовникам (spravka_inObjekt.xltx)
                  │                                      │
                  ▼                                      ▼
         «В работе» (inWork=1) ─────────────────► Садовник выполняет
                                                         │
Форма «task_manager» (результаты):  ◄────────────────────┘
  выбирается акт (done=0), вводятся: садовник, дата,
  литры в баке (tank), тип обработки, бензин, расход
  препарата = n_p × tank / 10   →   запись(и) в treat, done=1
                  │
                  ▼
Отчёты: журнал обработок (work_book), расход по препарату
за период (f_farma), по объекту (f_location), по садовнику
(f_person), бензин/масло (rep_gasolin), списание ТМЦ (of_report_form)
```

### 3.1. Модуль агронома: акт осмотра (форма `Inspection ADD`)
Порядок ввода:
1. Дата. После выбора даты форма считает, сколько актов уже есть на эту дату, и предлагает следующий порядковый номер.
2. Объект (список `location`) → куртина (список куртин объекта).
3. Растение (список `flora`). После выбора растения форма ищет похожие прошлые акты по связке объект + растение и показывает их списком. Кнопкой можно взять причину и описание из прошлого акта и записать ссылку `prev_insp` (повторное обращение).
4. Количество (`count`, текст), инвентарный номер (`inv`), описание.
5. Причина: переключатель типа (вредитель / болезнь / физиология / другое), затем выбор из соответствующего справочника, с кнопкой «последствия» (меняет формулировку) и «добавить» (несколько причин через « + »). Формируются `reason` (полный текст), `reason_short` (краткие названия), `reason_tip` (тип, например «Вредители + Заболевания»). Из списка можно открыть форму редактирования справочника.
6. Меры (поле `farma`): выбор способа из шести вариантов (по листу; под корень; комплексно лист + корень; курс трёхкратно с интервалом 7–10 дней; внесение удобрения; другое). Список препаратов фильтруется по полю `farma.use`. После выбора препарата автоматически формируется текст вида: «Обработать по листу препаратом: Скор с н.п. 2 мл на 10 литров воды.» Можно добавить до трёх препаратов (смесь). Кнопки добавляют «По 10/20/30/40 литров на растение». Отдельно задаются дополнительные действия (`task`, справочник `task` из 41 типового задания) и срок `task_data`.
7. Сохранение (кнопка «Записать») создаёт строку `inspection` с полями: код акта (дата `ггггммдд` + двузначный порядковый номер, строкой), автор `Autor`, дата, объект, куртина, растение, `inv`, `count`, описание, причины, меры, `reag1..reag3`, `task`, `prev_insp`. Поля `done`, `inWork`, `task_data` при сохранении не заполняются: `done`/`inWork` меняются другими формами или вручную, а `task_data` в этом коде не пишется (источник значения не выяснен).
8. Кнопка выгрузки в Excel: акт обследования за выбранную дату по шаблону `insp_report.xltx`.

### 3.2. Модуль заданий садовникам
Печатается справка `spravka_inObjekt.xltx`: все акты с `done=0`, сгруппированные по объекту, колонки «Куртина, Растение, Кол-во, Описание проблемы, Меры по устранению, Доп. действия». Есть запросы `q_task_report`/`task_rep` для актов `inWork=1 AND done=0` и отчёт `task_report`.

### 3.3. Модуль внесения результатов (форма `task_manager`)
Показывает акты с `done=0`. Для выбранного акта в строке до трёх препаратов (`reag1..3`): вводится объём бака `tank1..3`, тип обработки `treat_type` (Обработка / Пролив / Внесение / Доп задание), признак «бензин» `gasolin`. Формулы:
- тип по умолчанию определяется по тексту меры: «Обработать по листу…» → `Обработка` + бензин=да; «Пролить под корень…» → `Пролив`.
- `reag_count = farma.n_p × tank / 10` (норма на 10 л воды умножается на литры бака).
- По кнопке «Записать» для каждого препарата создаётся строка в `treat` (`reag1`, `reag_count1`, `tank`, `Treat_type`, `gasolin`, `data`, `person`, `location`, `flora`, `reason` = id акта) и у акта ставится `done=1`.

Ограничение старой системы: связь «обработка → акт» через поле `reason` (числовой id акта); `person`, `flora`, `reag1`, `location` в `treat` хранятся как свободный текст, а не ссылки.

### 3.4. Учёт расхода препаратов
- `q_farma` / форма `f_farma`: расход выбранного препарата за период по объектам (`UNION ALL` по `reag1..reag4`).
- `q_location` / `f_location`: расход всех препаратов на объекте за период с причиной, растением и единицей.
- `q_person` / `f_person`: обработки садовника за период (дата, объект, бак, препараты).
- `person_tank`: суммарные литры по садовникам.
- Отчёт «Расход по действующему веществу» в старой системе отсутствует. В таблице `farma` нет данных о действующем веществе (ДВ) и его содержании.

### 3.5. Бензин и масло
Запрос `q_gasolin`: для обработок с `gasolin=True` за период: бензин = `tank × 0.008`, масло = `tank × 0.00016` (т.е. 8 мл бензина и 0,16 мл масла на литр раствора). Отчёт `o_gasolin`.

### 3.6. Списание ТМЦ (форма `#of_report_form`, отчёты `farma_report_oficial`, `q_of_farma_report`)
Бухгалтерская процедура:
1. Выбирается препарат. Подтягиваются складские реквизиты (`farma_code`, `sklad_name`, `sklad_pref`, `n_p`).
2. Список обработок после даты (в коде зашита `01.01.2023`) с `write-down=False`, соединённых с `location.loc_code`.
3. Двойным щелчком строки переносятся из левого списка (не списано) в правый (в отчёт). Значение расхода строки можно скорректировать (при этом пересчитывается `tank = количество × 10 / n_p`).
4. Нажатие кнопки заполняет вспомогательную таблицу `farma_report` (`place_id`, `farma_id`, `farma_name`, `farma_count`, `coment`) и выводит Excel по шаблону `farma_report.xltm` («Отчёт о расходовании ТМЦ») и накладную СУ-21 `doc_report.xltx`.
5. Пометка `write-down` ставится на списанные записи (поле есть в `treat`: 2470 из 10291 помечены).

В таблице `farma_report` (локальная в BD_forms) лежит 34 строки старых итогов («Собственные нужды» — это объект СК-5 по примечанию в шаблоне).

### 3.7. График защиты (формы `#protection`, `#prot_scheduler`, таблица `protection`)
Календарь профилактики: запись = неделя года (`prot_data` 1–52) + фаза развития (`prot_phenology`: «Начало вегетации», «Розовый конус», «Окончание цветения», «Созревание плодов» и т.д.) + растение (`prot_subject` = `flora.ID`, например 171 = «Роза») + объекты защиты (вредители/болезни) + препараты через `;`. Всего 7 записей. Планировщик показывает текущую, предыдущую и следующую недели. Форма помечена `#` (вероятно, в разработке).

### 3.8. Справочники и служебное
Формы `f_pest`, `f_sickness`, `f_physiology`, `f_other`, `f_task`, `f_flora`, `f_farma`, `f_place`, `f_locatoin`, `person_gid`, `place_gid`, `flora_gid`, `farma_gid` — простые формы редактирования справочников. Форма `main` — меню. `#Flora_place` — состав растений куртины (редактирует текст `place.content`). Таблица `docs` (6 записей) хранит ссылки на акты и фото (пути к файлам, которых нет в репозитории). Модуль `JsonConverter` — стороннее подключение, самой системой не используется.

## 5. Выявленные проблемы данных (для миграции)

Все цифры получены из `BD_table.accdb`.

1. **Текстовые ключи без целостности.** В `treat`/`inspection` растения, препараты, садовники, объекты хранятся текстом.
   - Препараты в `treat.reag1`: 57 написаний отсутствуют в `farma` (регистр, опечатки: «корневин», «фалькон», «актеалик», «максифол рутфарм»); в `reag2` 2.
   - Растения: 34 написания в `inspection.flora` и 35 в `treat.flora` не найдены в справочнике (регистр, пустые, «Все растения», «Сосна  чёрная» с двойным пробелом).
   - Садовники в `treat.person`: 48 различных написаний при 28 записях в `person` (ФИО без инициалов, разный регистр).
2. **Дубли в справочнике препаратов:** 12 записей `farma` с одинаковым названием (с учётом регистра и пробелов), а значения `farma.class` и `farma.use` написаны по-разному (`Удобрение/удобрение`, `по листу/по литсу`).
3. **Нормы хранятся текстом:** `n_p` в основном число («10», «20»), но есть пустые (4) и мусор (например «10мл на 10 литров воды» в поле нормы). Десятичные записаны через запятую («0,2»). Единицы: «грамм», «г», «гр», «мл», «шт».
4. **Разрыв ссылок:** 4 акта ссылаются на несуществующую куртину; 4 обработки ссылаются на несуществующий акт; 21 обработка с препаратом без расхода.
5. **Аномальные значения:** объём бака `tank` до 100 000 (при медиане 30 л). Явные ошибки ввода, их надо показать пользователю, а не править молча.
6. **Нет ДВ:** действующее вещество и его содержание в базе отсутствуют, поэтому расход по ДВ без новых данных посчитать нельзя.
7. **Нет понятия нормы по культуре.** Единственная норма — одна на препарат. Повышенные нормы вносились вручную в текст акта («По 20 литров на растение») или правкой `reag_count`.
8. **Незавершённые обработки:** у 24 записей `treat` дата не разобралась (пустая/некорректная), у 1 акта тоже.
9. **Дублирование кода:** в Access три копии формы ввода акта (`Inspection ADD`, `#Inspection ADD1`, `treat_add`) с почти одинаковым кодом.
10. **Привязка к Z:\\BD_SPS и Excel/COM.** Печать работает только на машине с Excel и сетевым диском.

## 9. Что и как проверялось

- Таблицы и данные читались утилитами `mdbtools` (`mdb-export`, `mdb-schema`) на Linux. Количество строк и значения сверены в pandas.
- Список форм, отчётов, запросов взят из системной таблицы `MSysObjects`; SQL запросов восстановлен из `MSysQueries`.
- Код VBA извлечён распаковкой (MS-OVBA) потоков из `MSysAccessStorage`. Компоновка самих форм (расположение и внешний вид полей) не восстановлена, только их имена, источники данных (RecordSource/RowSource) и код событий. Чтобы увидеть формы визуально, нужно открыть `BD_forms_1 (1).accdb` в Access.
- Чистый Python-пакет `access-parser` на этих файлах не работает (ошибка `KeyError: 4096` при чтении каталога), поэтому для импорта выбраны другие способы (см. ТЗ, раздел 8).
- Шаблоны Excel прочитаны через `openpyxl` (тексты и структура). Визуальное оформление не оценивалось.
- Не проверялось: работа на Windows, открытие в самом Access, содержимое папок Z:\\BD_SPS (отсутствуют), правильность ДВ и норм (данных нет).
